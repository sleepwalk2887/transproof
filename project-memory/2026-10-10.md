
## v4.17.0 术语「集合」+ LLM 智能扫描（已上线）

- 用户请求：术语库/专有译词库「不好用」——导入 PDF 只能识别分段文本、无法智能批量操作；要求能扫描 pdf/doc/txt 并「智能收纳整理为分开的集合」，翻译相关文章时可选取集合使用，避免把标题目录都当作术语的低级错误。要求先去 GitHub 开源取经、借鉴最优方案、最大自动化 + 去噪、合并两个库的功能。
- 取经结论：① 阿里云《翻译服务里的术语一致性工程》——glossary 构建流水线 = 预扫描抽高频名词短语（TF-IDF+词性过滤）→ 每个候选术语调一次「定译名」请求 → 低置信度进人工确认 → 定稿随翻译请求下发；② LlamATE（github.com/honghanhh/terminology2024）——用 LLM in-context learning 做术语提取 + self-verification。本实现取「LLM 抽词 + 置信度分级（高自动确认 / 低留待审核）+ 集合收纳 + 翻译时按启用集合注入」这一核心思路，落到现有单文件架构。
- 实现（工作副本 `C:\Users\Andrew\.dsh\dsh_orb\transproof\index.html`）：
  1. **数据模型**：`GLOSS_DEF` 升 version 2，新增 `collections: []` 数组；term 增 `collections` 字段；glossIngest 合并时保留集合归属。
  2. **智能扫描**：新增 `smartScanFile(file,onProgress)` —— `parseFile` 取 fullText → `splitChunks`（2500 字分块）→ 逐块 `callModel(SCAN_SYS,...)` 让 LLM 按 system prompt 抽取术语（强制排除章节标题/目录/页眉页脚/脚注/参考文献/普通词，只输出 JSON 数组 `{foreign,zh,type,note,conf}`，conf=high/mid/low）→ `extractJsonArray` 稳健解析（剥 markdown 围栏/前后缀、逐个 `{...}` 兜底）→ 按 fKey 去重 → 建集合（名字取自文件名）→ 高置信度且有中文译名的自动 `status=confirmed + recommend=rec`，其余留 `pending` 待审核。这正是「去噪」关键：标题目录被 system prompt 显式排除，低置信度不自动入定稿。
  3. **集合管理**：`renderCollections` 渲染集合卡（勾选启停 / 重命名 / 删除）；`openCollectionPicker` 在翻译工作台弹「选集合」多选弹窗。
  4. **注入过滤**：`buildSystem` 术语锁定从「全部 confirmed」改为「启用集合内的 confirmed」（`termActive(t)`，未分组术语恒 true 保持向后兼容）。
  5. **入口打通**：p-gloss 与 p-term 各加「🤖 智能扫描」按钮（`.pdf/.docx/.doc/.txt/.md`），扫完入专有译词库，可审核后「⚡同步到术语库」。
- 收尾（用户补的 #2/#3）：`#g-version` 标签由写死 "v3.0" 改为读 `APP_VERSION`（新增 `const APP_VERSION = '4.17.0'`，`window.TransProof.version` 同步）；`HANDOFF.md` 版本号/测试数/功能清单/测试方式（`node serve.js`）/node 路径同步更新。
- 测试：新增 3 个 Playwright 测试（`15-collections.js` 数据模型与 UI、`16-scan-funcs.js` 解析/分块纯函数、`17-scan-e2e.js` mock callModel 走完整扫描流程），全量 `run-all.js` **17/17 全绿**、全程 0 console error / 0 page error。
- 版本 4.16.1 → 4.17.0。已同步到部署源目录 + canonical（发布由用户在 WorkBuddy 侧说「发布 transproof」完成）。

## v4.18.0 校对前「质量预估」（P1 遗留项，已完成）

- 需求来源：`校对改进建议.md` P1 第 6 项「质量预估」，借鉴 qe4pe / divemt 的工作量预估——正式校对前，AI 花很少 token 快速扫一眼，给出「译文大概什么水平、哪些段落问题最集中、建议一校还是二校」。
- 实现：
  1. 校对工作台按钮行（btn-ext 旁）加 `#btn-estimate`「📊 质量预估」按钮，事件 `$('#btn-estimate').onclick = estimateQuality`。
  2. `estimateQuality()`：校验 apiKey/baseUrl/model 与译文非空 → 只取原文前 2000 字 + 译文前 4000 字（省 token）→ `callModelSimple(EST_SYS, user, 900)` 非流式调用（temperature 0.4、max_tokens 900）。
  3. `EST_SYS` system prompt：只输出一个 JSON 对象 `{score(0-100), level(S/A/B/C/D), summary, hotspots[{para,issue}]≤3, suggestStage(一校/二校), effort(小/中/大)}`，不做逐句修改。
  4. 新增 `extractJsonObject()` 解析单个 JSON 对象（剥 markdown 围栏、定位首 `{` 尾 `}`），与既有的 `extractJsonArray`（术语数组）区分——**这是本轮发现并修的一个隐患**：初版误用 `extractJsonArray` 解析对象，因 hotspots 数组的 `[` `]` 干扰，`indexOf('[')` 定位到热点数组而非外层对象，导致解析错位。
  5. `renderEstimate(o)`：弹窗渲染圆形评分（按分数着色：≥85 绿 / ≥70 黄 / ≥50 橙 / <50 红）+ 等级 + 一句话总结 + 「建议阶段」「预计工作量」标签 + 问题集中段落列表 + 底部提示「非逐句校对」。
- 测试：新增 `tests/18-estimate.js`（按钮存在 / 空译文不弹窗 / mock callModelSimple 渲染评分等级总结阶段工作量热点 / markdown 围栏 JSON 容错），全量 **18/18 全绿**、0 console error / 0 page error。
